# opencontrib

An automated agent that uses your Claude Pro/Max subscription during idle overnight hours to make
real contributions to open source projects while you sleep.

---

## What it does

Claude Pro and Max subscriptions include a usage window that resets every 5 hours. If you sleep
8 hours and work 8 hours, several of those windows pass completely unused. opencontrib puts those
idle hours to work: it runs nightly on a schedule, finds open issues in projects you care about,
writes fixes in a sandboxed environment, and opens pull requests under your GitHub account.

The contributions are real code changes against real issues — not summaries or suggestions. The
agent reads the codebase, writes a fix, runs the tests, and produces a PR that a maintainer can
actually evaluate. The agent does not target issues that are already being worked on, does not
touch repos that have asked not to receive automated contributions, and always discloses
that the PR was generated by an AI agent.

opencontrib is designed to stay in the background. It does not saturate your 5-hour usage window
— the per-session turn cap and nightly issue limit are both set conservatively so you still have
subscription headroom when you wake up. If something goes wrong in a job (the agent gives up, the
tests fail, the diff fails validation), it stops and logs the reason. No broken PRs are opened.

## How it works

### Scheduler and orchestrator

A cron job runs once nightly and kicks off the orchestrator process. The orchestrator reads your
`opencontrib.yml` config, finds eligible issues, and runs each issue as an isolated job. It tracks
what has been attempted tonight and stops when it reaches your configured limits.

The orchestrator also runs a continuous monitoring loop (every 10 minutes) that watches open
opencontrib PRs for review comments and CI failures, and queues follow-up jobs when they arrive.
Follow-up jobs are batched with a 2-hour debounce — multiple signals on the same PR are handled
in a single run, not one per comment.

### How issues are selected

The orchestrator scans your target repos for open issues in priority order:

1. Issues with a bot-welcome label (e.g., `bot-welcome`, `ai-ok`, `llm-ok`, or labels identified
   from the repo's CONTRIBUTING.md)
2. Bug issues (`bug`, `confirmed-bug`, `regression`)

Issues are skipped if: they have an open PR already, they were opened less than 24 hours ago,
someone is already working on them, the repo has indicated it does not want automated
contributions, or a previous opencontrib claim is still active.

`good-first-issue` is always skipped — those are reserved for human contributors.

For wildcard targets (e.g., `sindresorhus/*`), only bot-welcome issues are eligible. For repos
you list by full name, bug issues are also considered.

### Sandboxed containers

Each issue is handled in a fresh, ephemeral Docker container. The container:
- Mounts a named Docker volume that holds the cloned repo and installed dependencies (persistent
  between runs, created once at init time)
- Has its own separate memory volume for the agent's accumulated repo knowledge
- Has no access to the host filesystem
- Has no `GITHUB_TOKEN` — the agent cannot push code or open PRs on its own
- Has network access limited to GitHub, standard package registries (npm, PyPI, crates.io,
  proxy.golang.org), and Anthropic's API

The container is automatically deleted when the agent exits. The orchestrator then inspects the
agent's file changes, validates the diff, performs all git operations, and opens the PR via the
GitHub API.

### Claim comments

For bot-welcome issues, opencontrib posts a claim comment before starting work:

```
<!-- opencontrib-claim expires="..." -->
[opencontrib] Working on a fix for this issue.
If you're already working on this or would prefer a human contribution, reply and this claim will be released.
```

The claim expires after 6 hours. Other opencontrib instances (and future runs of your own) see
the claim and skip the issue. If the agent finishes, the comment is updated with the PR link. If
opencontrib crashes, the claim expires naturally and the issue becomes available again.

For bug issues, no claim is posted until a PR exists. If the agent cannot produce a fix, it
leaves no trace in the issue.

### PR disclosure

Every PR opened by opencontrib includes a mandatory disclosure:

```
Note: This PR was created by opencontrib, an automated agent using Claude. A human reviewed the
contribution config but did not manually author this code. Please review carefully. If you'd
prefer not to receive automated contributions, add a no-ai-prs label or note in your
CONTRIBUTING.md — opencontrib will respect it.
```

This is non-negotiable. PRs without disclosure are not opened.

## Getting started

Requirements: Docker, Node.js >= 20, a `GITHUB_TOKEN` with `repo` and `read:org` scopes,
and an `ANTHROPIC_API_KEY`.

```bash
# Guided setup (recommended — an AI agent walks you through configuration)
claude "set up opencontrib for me"

# Or, if you already have a config file:
claude "set up opencontrib using https://raw.githubusercontent.com/you/dotfiles/main/opencontrib.yml"

# Or, manual setup:
npx opencontrib init --config ./opencontrib.yml
```

The guided setup (`claude "set up opencontrib for me"`) uses the `AGENTS.md` in this repo to
know what to do. The agent will ask you a few questions, explain what will happen, and then call
`npx opencontrib init` once you confirm.

## Configuration reference

Configuration lives in `opencontrib.yml`. This file contains only decisions that belong to you —
safety rules, filtering logic, and contribution constraints are hardcoded in the orchestrator and
cannot be changed via config.

```yaml
targets:
  repos:
    - "sindresorhus/*"       # all repos in an org (wildcard — bot-welcome issues only)
    - "owner/specific-repo"  # specific repo (bug issues also eligible)
  languages:
    - typescript
    - javascript
    - python
    - rust
    - go

schedule:
  max-issues-per-night: 2    # new issue jobs per nightly run
  max-followups-per-night: 3 # PR follow-up jobs per nightly run (separate budget)
  max-issues-per-repo: 1     # don't touch the same repo twice in one night

autonomy:
  pr-mode: draft             # draft | publish

agent:
  driver: claude             # claude | gemini | codex | opencode
  max-turns: 30              # turn cap per issue session

notifications:
  webhook: https://ntfy.sh/your-topic  # optional
```

| Field | Type | Default | Description |
|---|---|---|---|
| `targets.repos` | list | required | Repos or org wildcards to target. |
| `targets.languages` | list | required | Languages to work in. Determines which Docker base image is used. |
| `schedule.max-issues-per-night` | int | 2 | Maximum new issue jobs per nightly run. |
| `schedule.max-followups-per-night` | int | 3 | Maximum PR follow-up jobs per nightly run. |
| `schedule.max-issues-per-repo` | int | 1 | Maximum issues attempted per repo per night. |
| `autonomy.pr-mode` | string | `draft` | `draft` opens PRs as drafts. `publish` opens them as ready for review. |
| `agent.driver` | string | `claude` | Which coding agent CLI to use. |
| `agent.max-turns` | int | 30 | Maximum turns per agent session. Controls subscription consumption. |
| `notifications.webhook` | string | none | Optional ntfy.sh or compatible webhook URL for run summaries. |

## CLI reference

```bash
npx opencontrib init    # One-time setup: validate config, fork repos, create Docker volumes,
                        # install cron job. Safe to re-run after a failure.

npx opencontrib sync    # Re-read config, update volumes and schedule. Re-analyzes all target
                        # repos for AI-hostility and bot-welcome labels. Run after config changes.

npx opencontrib check   # Validate credentials and run a dry-run of the opportunity finder.
                        # Shows which issues would be targeted tonight. Does not make changes.

npx opencontrib run     # Run the orchestrator manually (this is what the cron job calls).

npx opencontrib teardown # Remove the cron job, Docker volumes, and optionally GitHub forks.
```

## Security

### What containers can and cannot do

Each agent runs in an ephemeral Docker container with these constraints:

- **No host filesystem access.** The container only sees its repo volume (`/workspace`) and the
  agent memory volume (`/root/.claude`). No bind mounts to the host.
- **No GitHub token.** The `GITHUB_TOKEN` is never injected into the container. The agent cannot
  push code, open PRs, or make GitHub API calls. All of that is done by the orchestrator on the
  host after the agent exits.
- **No git.** The agent's tool whitelist excludes git. Branch creation, committing, and pushing
  are all handled by the orchestrator.
- **Restricted outbound network.** Containers are attached to a Docker bridge network with
  iptables rules that allow only: `github.com`, `api.github.com`, `registry.npmjs.org`,
  `pypi.org`, `crates.io`, `proxy.golang.org`, and `anthropic.com`. All other outbound traffic
  is dropped.
- **Resource limits.** Each container is capped at 2 GB RAM and 1.5 CPUs.

### Why the GitHub token stays on the host

The token has write access to your forks and the ability to open PRs into upstream repos. If a
malicious repo could steal it, that would be a significant account compromise. By keeping the
token on the host and out of containers entirely, an adversarial repo has no path to it — even if
the agent is fully compromised.

### Prompt injection defense

Public repos can contain adversarial content designed to manipulate the agent. opencontrib defends
against this in layers:

1. **System prompt framing.** The agent's system prompt names the threat explicitly and instructs
   the model to treat all repo content as data, not instructions. Any text that looks like
   instructions (e.g., "ignore previous instructions") triggers an `INJECTION_DETECTED` output
   and the job is abandoned.

2. **Container isolation.** Even if the model is fully compromised, the container cannot reach
   arbitrary hosts, access the host filesystem, or perform git operations. The blast radius of a
   successful injection is limited to the contents of the repo workspace volume.

3. **Diff validation before PR.** The orchestrator runs deterministic checks on everything the
   agent wrote before any git operation occurs: no changes to CI config or build files, no new
   dependencies added, no binary files, no credential patterns in modified files, and a line
   count cap.

### How to tell opencontrib to leave your repos alone

Add a `no-ai-prs` label to your repo, or include any of the following phrases in your
CONTRIBUTING.md or README:

```
"no ai", "no llm", "no chatgpt", "no claude",
"ai-generated code", "automated contributions", "human only", "no bots"
```

opencontrib checks these at `init` and `sync` time and will never target a repo that matches.

## For repo maintainers

If you received a PR from opencontrib, here is what you should know.

### How to identify it

- The PR description includes a disclosure block: "This PR was created by opencontrib..."
- The branch name follows the pattern `opencontrib/issue-<n>-<slug>`
- The author is a GitHub user running opencontrib on their own account (not a bot account)

### What it is

opencontrib is a tool that individuals run locally or on a VPS to make open source contributions
using their Claude subscription during idle hours. The person who submitted this PR configured
opencontrib to target repos in your area, and the tool identified an open issue and produced a
fix. A human set the configuration, but the code was written by the AI agent.

### How to stop receiving them

Add a `no-ai-prs` label to your repo, or add a note to your CONTRIBUTING.md saying you do not
accept AI-generated or automated contributions. opencontrib checks these at setup time and will
not target your repo once either signal is present.

You can also comment on an issue with something like "please don't" or "I'll take this" —
opencontrib monitors active runs for objection comments and will stop and release the claim.

### The claim comment format

For issues that are explicitly marked bot-welcome, opencontrib posts a claim comment before
starting work. It looks like this:

```
<!-- opencontrib-claim expires="2026-03-14T08:15:00Z" -->
[opencontrib] Working on a fix for this issue.
If you're already working on this or would prefer a human contribution, reply and this claim will be released.
```

The HTML comment is machine-readable and used to prevent multiple opencontrib instances from
working on the same issue simultaneously. The claim expires automatically if opencontrib does not
finish — it does not permanently hold the issue.

## Open questions and known limitations

These are unresolved design questions. They are documented here honestly, not papered over.

**Fine-grained PAT scope for forks.** It is unclear whether a GitHub fine-grained PAT can be
scoped to only the forked repos under your account, or whether it needs broader `repo` scope.
Until this is resolved, the setup guide asks for full `repo` scope, which is broader than ideal.

**AGENTS.md conflicts.** Target repos can include their own `AGENTS.md` files with instructions
for AI agents. If a repo's AGENTS.md asks the agent to do something opencontrib disallows (e.g.,
run a custom install script), the behavior is currently to log a conflict and let opencontrib's
security rules win. A future version should surface these conflicts to the user at `sync` time
rather than silently overriding.

**Fork merge conflicts.** opencontrib syncs each repo workspace with upstream before each job.
If a previous opencontrib branch has a merge conflict with the current upstream state, the job is
aborted and logged. There is no automatic conflict resolution — the conflicting branch must be
cleaned up manually or via `opencontrib sync`.

**max-turns calibration.** Users may not have an intuitive sense of how many turns a typical
small fix takes. A future version of `opencontrib check` may run a dry-run and report a turn
estimate, so users can tune the cap with real data.

**Multi-instance coordination.** If two people run opencontrib under the same GitHub account,
they share token rate limits and can see each other's claim comments, but have no shared state
for spend tracking. This is an edge case but worth knowing if you share an account.
